## Windows GNU raw-dylib linker workaround (build helpers under E:\SwiftGet\.toolbin, git-ignored)
This host is `x86_64-pc-windows-gnu` with an incomplete self-contained MinGW: GNU
`dlltool` cannot run (no bundled `as.exe` assembler), and LLVM's `dlltool`
produces corrupt `raw-dylib` import tables (duplicate import descriptors / null
IAT thunks) once feature-unified `windows-sys` grows large, causing a
STATUS_ACCESS_VIOLATION (0xC0000005) at process startup. To build real, runnable
binaries C-compiler-free, the project:
- Patches `windows-link` (vendored at `vendor/windows-link`, committed) so the
  `windows-*` crates link the classic way (`kind = "dylib", modifiers =
  "+verbatim"`) instead of via raw-dylib. See root `Cargo.toml` `[patch]`.
- Puts correct MinGW-style import archives, each named after its verbatim DLL, in
  `.toolbin/winlibs` and adds that dir to the linker search path (see
  `.cargo/config.toml`). They are generated by `.toolbin/gen-winlibs.ps1`, which
  reads the real export tables of read-only system DLLs in C:\Windows\System32
  with `llvm-objdump` and feeds `.def` files to `llvm-dlltool` in plain archive
  mode. No system file is modified.
- Keeps `.toolbin/dlltool-wrap.exe` (a tiny shim that strips the GNU-only flags
  rustc passes to `dlltool` and forwards the rest to `llvm-dlltool.exe`) as the
  `-Cdlltool` for the few crates (e.g. `getrandom`) that use raw-dylib directly
  rather than through `windows-link`.
`.toolbin/` is git-ignored because its contents (a ~67 MB `llvm-dlltool.exe` copy
and host-derived system import archives) are large and host-specific;
`gen-winlibs.ps1` regenerates `winlibs` on this machine. Nothing here touches
PATH/registry/system state.
